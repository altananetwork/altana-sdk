# grantSession

Grant a scoped session key for a wallet. The admin signer authorizes the session onchain; from that point forward the session can act on the wallet within its permissions, enforced onchain.

```ts
import { createClient, BNB, signerFromPrivateKey } from "@altananetwork/sdk";

const client = createClient({ chains: [BNB] });
const admin = signerFromPrivateKey("0x...");
const wallet = await client.createWallet({ signer: admin });

const session = await client.grantSession({
  wallet,
  signer: admin,
  permissions: {
    calls: [{ to: "0xUniswapRouter..." }],
    spend: [{
      limit: 50n * 10n ** 18n,    // 50 USDT. Note: 18 decimals on BNB Chain.
      period: "day",
      token: "0xUSDT...",
    }],
  },
  expiry: Math.floor(Date.now() / 1000) + 7 * 24 * 60 * 60, // 7 days
});

if (session.status !== "granted") throw new Error("grant failed");
// Hand `session` to whichever process runs the agent.
```

`grantSession` authorizes the session on every chain the client was configured with, or on the chains you pass in `chainIds`. It never throws for a failed step: check `status`.

:::warning[Spend limits are raw token units, and decimals differ by chain]
`limit` is denominated in the token's smallest unit, so you need that token's decimals on that chain. USDT and USDC use **18 decimals on BNB Chain** and 6 on Ethereum. Writing `100_000_000n` for "100 USDT" on BNB sets a cap of 0.0000000001 USDT, and the agent's payments revert against a limit that looks generous.
:::

:::warning[The spend cap also pays relay fees]
Every transaction's relay fee is paid out of the session's spend cap on the fee token, so the cap covers fees, not just what the agent sends. A near-zero native cap (say, 1 wei "so the agent can't spend anything") creates a session that can never execute a single transaction: the relay rejects each bundle before inclusion (`FAILED`, `statusCode` 300, see [Errors](/sdk/errors)). Leave fee headroom in the cap on top of the agent's intended spending. Where the relay accepts other fee tokens (on Celo: USDC, USDT, USDm, EURm, KESm), a session pays fees from whichever capped token the wallet holds; pass `feeToken` to `grantSession` to add the cap for a stablecoin.
:::

## Registering the session key

The session's public key is written to [Keystore](/concepts/keystore) via the Controller, batched into the same userOp — controlled by the `register` flag, on by default. Registration is what makes the key's authority **provable to anyone**:

- **Third parties can verify it on-chain** — other agents, counterparties, dashboards, and compliance tools can check the key's authority, expiry, and revocation state (`getKeys` / `isValidKey`, or the MCP `verify_authorization` tool) without trusting you or Altana. Reads are free and unlimited.
- **Keys are discoverable** — a wallet's keys can be enumerated from chain for recovery and auditing.
- **Grants and revokes leave an on-chain trail** — timestamped, monotonic revocation.
- **(Ethereum)** one registration extends across chains via [`ensureKeyCached`](/sdk/sync-to-l2).

To skip registration (and its one-time fee), pass `register: false`. The session works the same, but Keystore readers like `verify_authorization` won't see it. Register it later at any time:

```ts
await client.registerSessionKey({ wallet, signer: admin, session });
```

## Parameters

```ts
client.grantSession(opts: ClientGrantSessionOptions): Promise<GrantSessionResult>;

type ClientGrantSessionOptions = {
  wallet: Wallet;
  signer: Signer;                  // the wallet's admin signer
  permissions: SessionPermissions;
  /** Unix epoch seconds. Most apps use Date.now()/1000 + N. */
  expiry: number;
  /** Bring your own session signer, or omit to let the SDK generate one. */
  sessionSigner?: Signer;
  /** Register the key in Keystore (default true). */
  register?: boolean;
  /**
   * L2s only: prove the Keystore entry into each L2 cache (default true). The proof runs on
   * after grantSession returns; "await" waits for it; false skips it.
   */
  populateCache?: boolean | "await";
  /** Progress, per chain where it applies. */
  onStatus?: (status: "registry-write" | "account-authorization" | "cache-sync" | "done",
              detail?: { chainId: number }) => void;
  /**
   * The token(s) the session may pay relay fees in, one address or a list.
   * Each gets a daily spend cap added to the session (default one whole
   * token; see feeSpendLimit), and the grant itself pays its fee with the
   * first one the wallet holds. Omitted, the relay charges whichever
   * accepted token the wallet holds.
   */
  feeToken?: Address | readonly Address[];
  /** The cap added for each fee token, in its smallest unit. Default one whole token per day. */
  feeSpendLimit?: bigint;
  /** The chains to grant on. Defaults to every chain the client was configured with. */
  chainIds?: number[];
};
```

A session pays relay fees only out of its spend caps: with no `feeToken` on an
execute, the SDK charges the capped token the relay accepts that the wallet
holds the most of. Pass `feeToken` here (one address or a list) so a session can pay
from a stablecoin the wallet holds (on Celo: USDC, USDT, USDm, EURm, KESm); the
returned `Session.permissions` carries the added caps, and `execute` must be
called with that session, not with the permissions you passed in. A token the
relay does not accept on any of the chains granted on is refused.

See [Sessions](/concepts/sessions) for the full permission shape reference.

## Returns

```ts
type GrantSessionResult = Session & {
  keyId: Hex;
  status: "granted" | "failed";
  legs: SessionLeg[];       // one per step per chain; see revokeSession for the shape
  cacheSync: Promise<SessionLeg[]>;  // the cache legs once their proofs are in
};

type Session = {
  walletAddress: Address;
  signer: Signer;          // session key. Agent signs with this.
  publicKey: Hex;
  permissions: SessionPermissions;
  expiry: number;
};
```

`GrantSessionResult` is a `Session`, so it goes anywhere a `Session` goes: `execute`, `revokeSession`, `registerSessionKey`, `signOrder`.

`status` is either `granted` or `failed`. It is `granted` only when every leg confirmed or had nothing to do; any failed leg makes it `failed`, and `legs` says which chain and which step. Each leg carries its own `transactionHash`, which is the receipt to record for the registration fee. Granting again with the same `sessionSigner` is safe: a key already valid in the Keystore is not written or charged twice.

## What lands onchain

For every chain you grant on, the SDK runs up to three legs:

1. **Registry.** One Keystore write per Keystore chain: `registerKey(session)`, preceded by `initialRegisterKey(admin)` on the wallet's first write, skipped when the key is already valid there. When the wallet holds no ETH on the Keystore chain, the relay funds the write from the wallet's balance on the L2 being granted on; the leg then carries `fundedFromChainId` and `sourceTransactionHash`. On a chain with its own Keystore (BNB, Ethereum) it rides in that chain's account leg, in the same userOp, so the registration and the authorization land atomically. For an [L2](/concepts/keystore#reaching-other-chains) it is a separate write on the L1, through the L1 relay (the testnet relay serves Sepolia). Two L2s behind the same L1 share one write.
2. **Account.** The session authorized on the wallet's smart account on that chain, through its relay, the fee paid in an accepted token the wallet holds there (or the `feeToken` you name). The chains run in parallel; an L2 waits for its L1 write and is skipped if that write failed.
3. **Cache.** On an L2, the proof of the Keystore entry into its KeyStoreCache, as a wallet call through the same relay (see [`syncSessionToCache`](/sdk/sync-to-l2#syncsessiontocache)). Skipped with `register: false` or `populateCache: false`.

The proof can only be built once the L2 has anchored the Sepolia block of the Keystore write, which on Celo Sepolia takes 15 to 30 minutes. `grantSession` does not make the user wait for that: it returns as soon as the registry write and the account authorizations are confirmed, which is when the session is usable (nothing in `execute` reads the cache). The cache legs then read `PENDING`, the proofs keep running, and `cacheSync` resolves with the finished cache legs. It never rejects; a proof that fails is a `FAILED` leg there. If your process exits first, the session still works and [`syncSessionToCache`](/sdk/sync-to-l2#syncsessiontocache) submits the proof later. Pass `populateCache: "await"` to get the old behaviour and return only once every proof is in.

## What it costs

`client.quoteGrantSession` takes the same options and returns one line per leg plus the payers' balances, without signing or sending anything. A registry line the relay funds from an L2 carries `fundedFromChainId` and is charged to the wallet's balance on that chain, not on the Keystore chain. A balance's `needed` is the fee plus the registration fee, not the registration fee alone (see [revokeSession](/sdk/revoke-session#what-it-costs)). A cache proof needs a Keystore entry to prove: after the first grant the quote proves one of the wallet's existing keys, which costs the same; on a first grant there is none yet, so those lines come back `deferred` (priced once the registry write lands) and `complete` is `false`.

## Persisting a session

A `Session` embeds the session's private key and bigint spend limits, so **never `JSON.stringify` it** — that throws on the bigints, and when it doesn't, it writes the secret into your storage while dropping the signing capability. The supported pattern splits the two halves:

```ts
import { generatePrivateKey } from "viem/accounts";
import { signerFromPrivateKey, serializeSession, deserializeSession } from "@altananetwork/sdk";

// Grant: bring your own key, and store it where you keep secrets.
const sessionKey = generatePrivateKey();
await secrets.save("agent-1.key", sessionKey);                 // keychain, KMS, env — yours

const session = await client.grantSession({
  wallet, signer: admin,
  sessionSigner: signerFromPrivateKey(sessionKey),
  permissions, expiry,
});
await db.save("agent-1.session", serializeSession(session));   // JSON-safe, contains NO secret

// Restore — any process, any time:
const restored = deserializeSession(
  await db.load("agent-1.session"),
  signerFromPrivateKey(await secrets.load("agent-1.key")),
);
```

`serializeSession` keeps `walletAddress`, `publicKey`, `permissions` (spend limits as decimal strings), and `expiry` — the values that must match the grant at execute time. `deserializeSession` restores the bigints and refuses a key that doesn't match the session's registered `publicKey`, so a mixed-up key fails loudly at restore instead of opaquely at execute.

If you omit `sessionSigner`, the SDK generates a key that exists **only in the current process's memory** and warns on the console: lose it (a crash, the script ending) and the on-chain authorization it backs is permanently unusable — revoke-and-regrant is the only exit.

## Notes

- **Persist both halves**: the serialized session (above) *and* the key, separately. An agent needs `permissions + expiry` to execute, not just the key.
- **`permissions.calls` omitted = unrestricted.** Always set both `calls` and `spend` unless you specifically want an open-scope session.
- **This is the call that costs the user money.** It pays a one-time [Keystore](/concepts/keystore) registration fee, and on a wallet's very first admin action it pays that fee twice, because `initialRegisterKey` for the admin is prepended into the same userOp. Record the legs' `transactionHash` if you show users a history of what they were charged for. Pass `register: false` to skip the registration fee entirely.
