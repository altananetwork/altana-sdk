# revokeSession

Revoke a session key everywhere it lives. One call finds the chains whose account holds the key, revokes it on each, revokes it in the [Keystore](/concepts/keystore), proves the revocation into every L2 cache, and reports each step per chain. After it confirms, the session's next execute attempt reverts at validation on every one of those chains.

```ts
// `client`, `wallet`, `admin`, and `session` from earlier
const result = await client.revokeSession({ wallet, signer: admin, session });
if (result.status !== "revoked") {
  console.error(result.legs.filter((leg) => leg.status === "FAILED"));
}
```

You can also pass just the session's public key:

```ts
const sessionPublicKey = "0x04..." as `0x${string}`;
await client.revokeSession({ wallet, signer: admin, session: sessionPublicKey });
```

A bare public key is read as secp256k1. Pass the `Session` for a passkey session, so the SDK revokes it as a WebAuthn P256 key.

## Which chains it acts on

`client.revokeSession` acts on every chain the client was configured with. There is no `chainId` option: pass the whole group, for example `createClient({ chains: [...NETWORKS.testnet] })`, and the SDK does the rest.

1. **Discovery.** In parallel, it reads which chains' accounts hold the key, and whether each Keystore behind those chains lists it as valid.
2. **Revoke.** In parallel, one account leg per chain holding the key, and one registry leg per Keystore that lists it. Two L2s behind the same L1 share one registry leg. When the Keystore chain is itself a chain holding the key (BNB, Ethereum), the registry revoke rides in that chain's account leg, in the same intent.
3. **Cache.** For each L2, once its registry revoke confirmed, a proof of the revocation into its KeyStoreCache, so readers on the L2 see the key as revoked.

## Result

```ts
client.revokeSession(opts: ClientRevokeSessionOptions): Promise<RevokeSessionResult>;

type ClientRevokeSessionOptions = {
  wallet: Wallet;
  signer: Signer;                 // the wallet's admin signer
  session: Session | Hex;         // the Session object or just its public key
  feeToken?: Address | readonly Address[];  // one token to force, or a list to choose from
  onStatus?: (status: "discovery" | "registry-write" | "account-revoke" | "cache-sync" | "done",
              detail?: { chainId: number }) => void;
  populateCache?: "await";        // return only once every cache proof is in
};

type RevokeSessionResult = {
  keyId: Hex;
  status: "revoked" | "failed";
  legs: SessionLeg[];
  cacheSync: Promise<SessionLeg[]>;  // the cache legs once their proofs are in
};

type SessionLeg = {
  chainId: number;
  kind: "account" | "registry" | "cache";
  status: "CONFIRMED" | "FAILED" | "SKIPPED" | "PENDING";  // PENDING: a cache proof still running, see cacheSync
  via?: "relay" | "eoa" | "bundled";   // registry legs
  transactionHash?: Hex;
  blockNumber?: bigint;                // registry legs
  fundedFromChainId?: number;          // registry legs the relay funded from an L2 balance
  sourceTransactionHash?: Hex;         // the L2 transaction that locked those funds
  keyStoreCache?: Address;             // cache legs
  l1BlockNumber?: bigint;              // cache legs
  cachedKey?: CachedKey;               // cache legs
  reason?: string;                     // why it was skipped or failed
};
```

The cache proofs wait for each L2 to anchor the Sepolia block of the Keystore revoke (15 to 30 minutes on Celo Sepolia), so `revokeSession` returns before them: the account legs are what stop the key, and they are confirmed by then. The cache legs read `PENDING` and `cacheSync` resolves with them once the proofs are in; until then that L2's cache still reports the key as valid to anyone reading it. Pass `populateCache: "await"` to wait.

`status` is either `revoked` or `failed`. It is `revoked` only when every leg confirmed or had nothing to do. Any failed leg makes it `failed`, and the other legs still run, so `legs` tells you exactly which chain and which step is left. Calling `revokeSession` again is safe: discovery only picks up what is still pending (an account still holding the key, a Keystore still listing it, a cache still showing it live).

`revokeSession` never throws for a failed leg. Check `status`.

## What it costs

A registry leg for a wallet with no ETH on the Keystore chain is funded by the relay from the wallet's balance on the L2 and carries `fundedFromChainId`; its cost shows on that chain in `quoteRevokeSession`.

`client.quoteRevokeSession` takes the same options and returns one line per leg (fee and native value, who pays) plus the payers' balances, without signing or sending anything. Each line's `needed`, and each balance's sum of them, is the native amount the leg needs: the fee plus the value it carries, such as a registration fee. When the wallet is short, the relay's own figure is used and `neededFromRelay` is `true`:

```ts
const quote = await client.quoteRevokeSession({ wallet, signer: admin, session });
for (const line of quote.lines) console.log(line.chainId, line.kind, line.fee);
```

Each leg is one signature today, so a revoke on two L2s is five: two account legs, one registry leg, two cache proofs.

## Keystore impact

Revocation calls Keystore directly, not the Controller. The call is gated onchain by `onlyKeyOwnerOrValidator`, so only the wallet itself (executing inside its own userOp) or a designated validator can revoke a key. A random caller reverts at the modifier.

Revocation is **monotonic**: once a key is revoked, it cannot be reactivated. To restore session access for a wallet, grant a new session with a fresh keypair.

Sessions granted with `register: false` (see [grantSession](/sdk/grant-session)) have no Keystore entry. For those, `revokeSession` skips the registry leg and revokes the account-level authority alone, which is what actually strips the session's power.

## Caches you populated yourself

`revokeSession` proves the revocation into the cache of every L2 in the client's chains. A cache it does not know about, such as one you populated with [`ensureKeyCached`](/sdk/sync-to-l2) on a chain outside the client, keeps reporting the key as valid until a post-revocation proof lands there:

```ts
import { syncKeyToL2, ETHEREUM, BASE } from "@altananetwork/sdk";

await syncKeyToL2({
  l1Client, l2Client, l2WalletClient,
  l1KeyStore: ETHEREUM.keyStore,
  l2Cache: BASE.keyStoreCache,
  user: session.walletAddress,
  publicKey: session.publicKey,
});
```

`ensureKeyCached` will **not** do this for you: it returns early when the cache reports the key as valid, which is exactly the state a stale cache is in after a revocation. Once a cache observes `revoked=true` it cannot be flipped back, even by a proof against an older L1 block.

## Notes

- Revocation does not require the session signer, only the wallet's admin signer.
- Revocation needs only the session's public key (`revokeSession` accepts `Session | Hex`). But keep the full serialized session ([`serializeSession`](/sdk/grant-session#persisting-a-session)) while the session is meant to keep working — an agent needs `permissions + expiry` to execute, not just the key.
- A failed revocation **returns** `status: "failed"` rather than throwing. Check the returned status; do not assume success because nothing was raised. See [Errors](/sdk/errors).
